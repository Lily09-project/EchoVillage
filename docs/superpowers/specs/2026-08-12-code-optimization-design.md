# Echo Village 相容式程式碼優化設計

## 目標

在不改變現有玩法、中文介面、操作方式、公開 API、場景節點路徑與存檔相容性的前提下，同時改善執行效能、記憶體配置、模組邊界與長期可維護性。

本次優化不是功能刪減或重新製作遊戲，而是替現有完整版本建立可持續擴充的內部架構。所有改動必須以可觀測的基準、特性測試與完整回歸測試證明安全。

## 現況與主要問題

### `scripts/main.gd`

- 約 1,080 行、69 個函式，同時負責輸入、玩家移動、鏡頭、導航、HUD、模態視窗、互動、Debug 與視覺 QA。
- `_process()` 每幀呼叫完整 `refresh_ui()`；即使遊戲資料沒有改變，仍會重算時間、資源、進展、NPC、記憶、任務與 Debug 文字。
- 多個 EventBus 訊號也直接觸發完整刷新，可能在同一幀產生重複工作。
- UI 建構與資料呈現緊密耦合，使局部功能難以獨立測試或替換。

### `scripts/core/game_manager.gd`

- 約 717 行、67 個函式，除了 facade 職責，仍直接管理資料載入、NPC 模擬、互動、社交、世界事件、任務、交易、進展與序列化協調。
- 專案已有 Inventory、Needs、Relationship、Progression 等服務，但部分領域邏輯仍留在管理器內。
- 多處 `duplicate(true)` 用於安全快照；存檔與隔離測試需要保留，但高頻 UI 通知與未變更資料可改用較輕量的邊界。

### 測試

- 現有單一 `tests/test_runner.gd` 約 861 行，涵蓋約 76 項功能、UI、存檔、模擬與資料契約檢查。
- 覆蓋面廣，但缺少 UI 刷新頻率、同幀去重、服務委派與效能回歸的明確契約。

## 已考慮方案

### 方案 A：局部效能修補

只移除每幀完整 UI 刷新並減少明顯深拷貝。改動小、交付快，但巨型腳本與耦合問題會保留，下一輪擴充仍會提高風險。

### 方案 B：一次性全面拆解

一次重寫主場景與遊戲管理器。最徹底，但修改面過大，難以分辨行為回歸來源，也不利於驗證舊存檔與 UI 節點契約。

### 方案 C：相容式分層重構（採用）

先建立基準與特性測試，再保留既有 facade/API/節點路徑，逐層替換高頻更新與領域實作。每個階段都能獨立驗證並在發現問題時停止，不需要一次承擔全部風險。

## 架構設計

### 1. 事件驅動 UI 與刷新排程器

`Main` 保留場景生命週期與頂層協調，但不再每幀重建完整 UI。新增具名 dirty 區域，例如：

- `TIME`：時鐘、日夜階段與時間倍率。
- `PLAYER_RESOURCES`：硬幣、背包摘要與製作狀態。
- `WORLD_EVENT`：活動事件與地點資訊。
- `NPC_DETAIL`：選取居民的需求、關係、記憶與對話。
- `QUEST`：任務追蹤與任務日誌。
- `PROGRESSION`：聲望、稱號與成就。
- `DEBUG`：僅在 Debug 面板可見時更新。

EventBus、玩家選取、面板開關與遊戲時間事件只標記對應區域為 dirty。排程器在當幀末端合併重複標記，每個區域最多刷新一次。

玩家移動、Camera2D 跟隨、必要動畫與短暫回饋仍可逐幀更新，但不得觸發完整資料快照。時鐘顯示由分鐘變化或倍率變化驅動，不依賴每幀輪詢。

### 2. 主場景控制器分工

在保留 `Main.tscn` 現有節點名稱與路徑的前提下，將 `main.gd` 的實作逐步委派至下列控制器：

| 控制器 | 責任 |
| --- | --- |
| `HudPresenter` | 格式化並更新 HUD、居民資訊與狀態摘要 |
| `ModalCoordinator` | 主選單、暫停、設定、背包、交易、任務、地圖與手札的互斥、焦點和暫停規則 |
| `InputController` | 輸入映射、離散快捷鍵與重複輸入防護 |
| `WorldInteractionController` | 鄰近居民判定、地點可見性、互動與玩家回饋 |
| `VisualQaController` | 可重複截圖情境與擷取流程 |

第一階段可先以 RefCounted 輔助類別或場景子節點控制器實作。外部測試仍透過 `Main` 的既有方法與節點路徑操作；`Main` 提供薄轉接方法，直到測試與呼叫端可安全遷移。

### 3. `GameManager` facade 與領域服務

`GameManager` 繼續作為 Autoload 與唯一相容入口，既有公開方法名稱和回傳格式保持不變。內部新增或補全下列領域服務：

| 服務 | 責任 |
| --- | --- |
| `NpcSimulationService` | 決策排程、狀態機、需求推進與行動執行協調 |
| `SocialInteractionService` | 玩家互動、NPC 對 NPC 社交、記憶與關係後果 |
| `WorldStateService` | 地點、公共資源、世界旗標與事件結果協調 |
| `QuestOrchestrator` | 任務條件、原子交付、完成獎勵與進展觸發 |
| `TradeService` | 買入、出售、動態價格與原子庫存／貨幣異動 |
| `GameStateSerializer` | v3 序列化、反序列化及 v1/v2 遷移後的狀態驗證 |

既有 `InventoryService`、`NeedsService`、`RelationshipService` 與 `ProgressionService` 繼續沿用。服務接收必要資料與依賴，不直接尋找場景節點，也不自行控制 UI。

### 4. 資料快照與配置策略

- 深拷貝保留於存檔、載入、測試隔離、外部可變資料邊界與需要不可變語意的 EventBus payload。
- UI 不再要求完整世界深拷貝；改為領域化、唯讀用途的小型 Dictionary 快照。
- 對 progression、inventory summary、NPC detail 等衍生資料使用版本號或 dirty 標記失效；資料未變時重用上次結果。
- 訊號 payload 只包含識別碼或改變的領域，接收端自行請求所需的小型快照。
- 不以犧牲正確性換取配置數下降；任何移除 `duplicate(true)` 的位置都必須有防止外部意外修改的測試。

## 資料流

典型玩家互動流程：

1. `InputController` 將離散操作交給 `Main`。
2. `Main` 透過 `GameManager` 的既有公開 API 執行互動。
3. `GameManager` facade 委派對應領域服務，服務原子更新狀態。
4. `GameManager` 發出精準領域事件，例如居民、背包或進展已改變。
5. UI 排程器標記對應區域，並在同一幀末端合併刷新。
6. `HudPresenter` 只讀取該區域需要的小型快照並更新既有 Controls。

## 錯誤處理與可觀測性

- 服務對非法 ID、數量、缺少資料與不合法狀態回傳具 `ok` 與原因的結果，不留下部分更新。
- facade 維持既有呼叫端所期待的回傳格式，必要時在邊界轉換錯誤。
- UI 排程器在 Debug 模式提供每區刷新次數、合併次數與最後刷新原因。
- 效能量測只在 Debug／測試環境啟用，不污染正式遊戲輸出。
- 存檔載入失敗不得覆蓋目前有效狀態；遷移完成後必須先驗證再套用。

## 測試策略

### 優化前基準

- 記錄靜止 10 秒、連續移動 10 秒、開啟居民面板、交易、任務與 Debug 情境的 UI 全量與分區刷新次數。
- 記錄代表性情境的平均／高分位幀時間與快照配置熱點；數值用於前後比較，不預設硬體絕對門檻。
- 保存現有 headless 測試、七日模擬、視覺 QA 與 `.bat` 啟動結果。

### 特性與單元測試

- 靜止時不得每幀執行完整 UI 刷新。
- 同一幀多個相同領域事件最多造成一次區域刷新。
- 不同領域只刷新受影響區域。
- facade 委派後的公開 API、回傳值與副作用與重構前一致。
- 輕量快照不可被呼叫端修改而污染遊戲狀態。
- v1、v2 與 v3 存檔可正確載入；v3 round trip 保持資料一致。
- 交易、任務獎勵、採集與社交後果維持原子性。

### 完整驗證

- Godot 4.2+ headless 全套測試全部通過。
- 七日加速模擬無錯誤、無狀態破壞。
- 主場景 headless 載入與實際視窗啟動成功。
- 視覺 QA 截圖與既有關鍵介面檢查無回歸。
- `run_echo_village.bat` 在目前 Windows 環境一鍵啟動成功。
- Godot 輸出不新增 parser error、runtime error 或未處理警告。
- 優化前後報告清楚列出 UI 刷新次數與效能差異。

## 完成標準

1. 現有玩法、畫面結果、中文內容、輸入、節點契約與公開 API 無回歸。
2. 舊存檔可直接載入且重新儲存為目前格式。
3. 靜止畫面不再每幀執行完整 `refresh_ui()`。
4. 同幀重複事件會被合併，Debug 面板能證明各區刷新原因與次數。
5. `main.gd` 與 `game_manager.gd` 的主要責任已委派至可獨立測試的模組；原檔成為薄協調層，而非以行數作為唯一成功指標。
6. 高頻路徑中的深拷貝與重算顯著下降，且不破壞資料隔離。
7. 所有既有測試與新增優化契約測試通過，並完成 headless、視覺、實際啟動與 `.bat` 驗證。

## 分階段交付邊界

1. 建立基準、刷新計數與特性測試。
2. 導入 dirty-region UI 排程器並移除全量逐幀刷新。
3. 抽出 UI 控制器，同時保留既有 Main 轉接 API 與節點路徑。
4. 逐領域抽出 GameManager 服務，每抽一個領域即跑完整回歸。
5. 收斂快照與深拷貝策略，加入資料隔離測試。
6. 拆分測試檔與測試支援工具，但保持單一一鍵測試入口。
7. 完成效能比較、視覺 QA、實際啟動、`.bat` 測試與文件更新。

## 非目標

- 不在本輪加入新玩法、NPC、地圖或內容量。
- 不重做視覺風格或改變玩家熟悉的操作。
- 不提高存檔版本，除非實作中發現無法透過相容轉接層解決的必要狀態；若發生必須先重新核准設計。
- 不為追求較少行數而製造只有轉發、沒有清楚領域價值的碎片化類別。
- 不以硬體相關的單一 FPS 數字作為唯一效能成功標準。

## 自我審查清單

- 設計保留 facade、節點路徑與存檔契約，避免大爆炸式遷移。
- 效能改善有可量測基準與刷新計數，不只依賴主觀感受。
- 深拷貝優化明確保留資料隔離與原子性要求。
- 每個階段都有可停止、可驗證的邊界。
- UI 與核心領域拆分皆有具名責任，未引入功能範圍擴張。
